# ECC (Everything Claude Code): insights transferable to PCEE

Date: 2026-11-20 · Author: ecc-scout (research teammate) · Not committed. These are findings and suggestions; the design decisions stay with the user and the lead.

## What ECC is

ECC is the repo `github.com/affaan-m/ECC` (the old name `everything-claude-code` redirects there; `gh repo view` reports name `ECC`). I read `main` at commit `4adeee6` (pushed 2026-11-20T01:13Z), `VERSION` 2.2.3, MIT licence (`LICENSE`), about 307k stars, 137 open issues. It is a single-maintainer "agent harness operating system": a Claude Code plugin (`ecc@ecc`) plus adapters for about 7 other harnesses, shipping about 70 agents (`agents/`), hundreds of skills (`skills/`), about 90 slash commands (`commands/`), a hooks runtime (`hooks/hooks.json`, `scripts/hooks/`), language rules (`rules/`), a selective installer (`manifests/`, `install.sh`), a JSON state-store schema (`schemas/state-store.schema.json`) and a Rust control plane in progress (`ecc2/`). Its stated loop is `plan -> test -> implement -> review -> verify -> remember -> improve` (`README.md`). It is mostly a catalogue of prompts and hooks, not an execution engine: there is no durable scheduler, retry policy or event log comparable to PCEE's engine spec. The most design-relevant parts are small: the learning pipeline, the gates, the hook profiles and the 2.0 roadmap.

## Insights

Paths are in the ECC repo unless marked otherwise. "Adopt" means take the idea nearly as is; "adapt" means take the shape and change it; "avoid" means do not copy.

| # | ECC mechanism | PCEE part | Transfer | Why |
|---|---|---|---|---|
| 1 | Observations are captured by hooks on every tool call, not by a skill the model chooses to run: "Skills are probabilistic -- they fire ~50-80% of the time", hooks fire 100% (`skills/continuous-learning-v2/SKILL.md`, section "Why Hooks vs Skills for Observation?") | Improvement loop §3 adapters (`observer` reads staged updates; `dream` reads reports) and engine event log | Adopt (principle) | The improvement loop's evidence should come from deterministic capture (engine events, `runs.jsonl`, hook-written rows), never from a model deciding to note something. The loop spec already says "code only; no model decides success"; this supports extending it to the input side. |
| 2 | Atomic "instinct" records: one trigger, one action, a 0.3-0.9 confidence, an evidence list, and a scope of `project` or `global`; promotion to global only when the same id is seen in 2+ projects with average confidence >= 0.8 (`skills/continuous-learning-v2/SKILL.md`, "The Instinct Model", "Instinct Promotion") | Improvement loop §3 `proposals` table; stage 10 project owner (per-project config) and its later federation | Adapt | PCEE proposals already carry evidence citations and a class. ECC's addition is the project-vs-global scope and the cross-project promotion rule: this is the shape for "a change proven in project A may be offered to project B", which PCEE stage 10 federation will need. Do not adopt the confidence number: ECC raises it when "user doesn't correct" it, which is a model-free heuristic with no control group. PCEE's half-and-half trial against the decision rule is stronger. |
| 3 | Proposal, verification, promotion and rollback are separate steps; a candidate playbook is promoted "only after a verifier proves that they improve a scenario without widening blast radius"; a regression fixture must show a bad proposal is rejected (`docs/ECC-2.0-REFERENCE-ARCHITECTURE.md`, "Self-Improving Harness Loop") | Improvement loop §2 to §5 and Testing | Adopt (as test) | PCEE has the same separation. The one thing to copy is the explicit regression fixture "a bad proposal is rejected": PCEE's Testing list covers revert and protected paths but has no case where a plausible-looking but harmful proposal passes the tick's signal and is stopped by a guardrail. Add one synthetic run log for it. |
| 4 | "Mechanical" Stop-hook gate: only machine-checkable facts (file mtimes, disk space, regex), "No AI inference"; blocks at most once because it exits 0 when `stop_hook_active` is true, so an unfixable condition cannot trap the session (`skills/delivery-gate/SKILL.md`) | Engine §10.1 heartbeat and progress timeouts, §13 approval holds, worker Stop hooks | Adopt (the once-only block) | PCEE holds and the teammate Stop hook already block. The loop-proofing rule is worth stating in the engine spec: any hook that denies a stop must degrade to a warning on the second attempt, and the engine, not the hook, owns the retry. Also: its regex "rationalization" check is warn-only because heuristics false-positive. Keep such checks warn-only in PCEE too. |
| 5 | Soft-delete garbage collection of config: rename to `.disabled`, then a trash folder, one `[y/n/skip]` per candidate with no yes-to-all, a cap of about 20 candidates per run, and a log with undo steps (`skills/config-gc/SKILL.md`) | Improvement loop §5 (revert) and the memory-consolidation and task-observer outputs; `docs/superpowers/improve/` | Adapt | The improvement loop only adds and trials changes; nothing retires a `kept` change, skill or rule that has stopped helping. A periodic "retire" proposal kind with the same soft-delete and undo log would close that gap. The per-candidate confirmation matches PCEE's high-authority class; for low authority PCEE can keep its evidence-based automatic path. |
| 6 | Hook profiles `minimal`, `standard`, `strict` via `ECC_HOOK_PROFILE`, per-hook kill switch `ECC_DISABLED_HOOKS`, stable hook ids in a sidecar with a fingerprint per entry so reordering or editing a hook is detected (`hooks/README.md`; `hooks/hooks.metadata.json`) | Engine §10.5 policy version; §13 hold patterns; improvement loop §6 protected set | Adapt | PCEE already records a policy version per spec. Stable hook ids plus a fingerprint is a cheap way to make "the hook set a spec ran under" part of that version and to make the protected-set check on `claude/plugin/hooks/**` content-aware instead of path-only. A profile switch is optional; PCEE's kill switches are env vars today. |
| 7 | Adversarial dual review: two reviewers on different models with no shared context, both must pass, rubric criteria each with an objective PASS/FAIL condition, fix and re-run fresh (`commands/santa-loop.md`) | Engine §3 job graph (review jobs) and the architect job; K2 quality watch | Adapt | The rubric-with-binary-criteria part transfers directly to PCEE review jobs and makes reviewer output machine-comparable across runs. The two-model requirement costs a second full review per task, which cuts against PCEE's cost goal (the Problem section); use it only for the escalation cases the architect already handles, not on every task. |
| 8 | Benchmark loop prerequisites: success threshold, hard constraints evaluated separately from the aggregate score, a frozen metric, sample set and evaluator, a search budget (max variants, time, spend), and a ledger entry per run in which failures stay in the denominator (`skills/benchmark-optimization-loop/SKILL.md`) | Improvement loop §1 outcomes and §2 tick; queue metrics decision rule | Adopt (two items) | PCEE has most of this. Two additions: a per-trial search budget (the loop caps concurrent trials at 2 and ends a trial at 15 specs without verdict, but sets no spend cap), and the explicit rule "failures remain in task-level denominators" in the tokens-per-task metric, so a trial cannot look cheaper by failing early. |
| 9 | A versioned state-store schema for sessions, skill runs (with outcome, failure reason, tokens, duration, user feedback), skill versions, decisions (with `supersedes` and `alternatives`) and governance events with `resolvedAt` and `resolution` (`schemas/state-store.schema.json`) | Engine §1 state tables and §10.4 journal; improvement loop §3 `proposals` | Adapt | Two fields worth copying: `decisions.supersedes` and `alternatives` (PCEE architect rulings are events; a link to the ruling they replace makes later audits and the memory-consolidation step easier) and a `skillVersion` on every run record so a skill trial can be attributed to the exact copy used. PCEE's `variants` field on the run record already does the second; check it also records the skill version hash. |
| 10 | Quantitative skill portfolio dashboard: success-rate sparklines, failure-pattern clustering, pending amendments and version history per skill (`commands/skill-health.md`, `scripts/skills-health.js`) | Improvement loop §5 digest and `improve outcome status`; morning report | Adapt | PCEE measures outcomes per spec, not per skill. Per-skill success rate over the run log would feed the proposal ranking step (loop §2.4) with data, and would find skills that are never used. The data PCEE needs is already in run records once `variants` and skill ids are logged. |
| 11 | Worktree lifecycle events named in one list: create, resume, pause, stop, diff, review, PR, merge-ready, conflict, stale, close, salvage; plus notifications for blocked CI, dirty worktrees, merge conflicts and stale review (`docs/ECC-2.0-REFERENCE-ARCHITECTURE.md`, "Worktree And Session Orchestration") | Engine §6 enqueue/split/run, §9 recovery, stages 4 and 5 (locks, merge queue) | Adapt | Useful as a checklist for the stage 4 and 5 event vocabulary: `stale` and `salvage` are not among the states in the engine spec. ECC's own repo also has a stale-PR salvage ledger (`docs/stale-pr-salvage-ledger.md` is listed in `docs/`; I did not read it), a sign that abandoned worktrees accumulate in practice. |
| 12 | A one-page "lane rules" contract for a bounded worker: one task, one branch, one PR or receipt, then stop; no ledgers about ledgers; the final message is the receipt (under 300 words); blocked means stop and say what is needed, do not poll; do not spawn subagents (`docs/LANE-RULES.md`) | Engine §2 workers; `claude/worker.md`; engine brief builder | Adopt (already close) | `claude/worker.md` already says nearly the same. The extra items are the word cap on the final report and "no receipts about receipts", which suit engine jobs, where the report is parsed. Add a size cap to the `report` event body. |

## What PCEE already does better or differently

- Durable execution. ECC has no scheduler, heartbeat, retry policy, intent/result journal or replay check. Engine §10 and §11 cover these; ECC's closest part is the Rust `ecc2/` control plane, which I only listed and did not read, and `docs/ECC-2.0-GA-ROADMAP.md`, also unread, which is a roadmap and not an implementation.
- Evidence for improvement. ECC's confidence score moves on heuristics ("user doesn't correct the suggested behavior"). PCEE's loop compares trial and control halves of real engine-run specs against a frozen decision rule, with guardrails and a protected set (loop spec §2, §4, §6). ECC's own roadmap lists this as future work ("scenario spec, proposer trace, verifier result, promoted playbook", `docs/ECC-2.0-REFERENCE-ARCHITECTURE.md`), and its only artefact is a read-only prototype under `examples/evaluator-rag-prototype/`, which I listed but did not open.
- Authority classes. ECC's `/evolve` and `/promote` commands turn clusters of instincts into skills, commands or agents (`skills/continuous-learning-v2/SKILL.md`), with no stated class for changes to the evaluator or the rules. PCEE's protected set, enforced at class derivation, at the merge step and at the hold patterns, is stricter.
- Cost control. ECC's `cost-aware-llm-pipeline` and `commands/model-route.md` give a three-way heuristic (haiku, sonnet, opus by complexity). PCEE's tier map with enforced effort and a dispatch gate, and the K2 token measurements, are stronger and measured.
- Install model. ECC offers selective install modules and profiles (`manifests/install-modules.json`, `docs/SELECTIVE-INSTALL-ARCHITECTURE.md`, the latter unread). PCEE is a single checkout the live install links into; no change needed.

## Risks

- **Licence.** MIT (`LICENSE`: "MIT License, Copyright (c) 2026 Affaan Mustafa"). Copying text or code needs the copyright and licence notice kept. Ideas and shapes do not. The README says "This repo is MIT-licensed forever", but it also sells a hosted tier (ECC Pro), which could change which new parts are open; check the licence on the commit you copy from.
- **Prompt-injection surface.** The repo is an installable bundle of prompts and hooks whose own README warns that "Third-party re-uploads and unofficial mirrors ... may contain malware" and says to install only from official channels (`README.md`). Its `CLAUDE.md` has a "Prompt Defense Baseline", which shows the maintainers see the risk. Anything copied into `claude/skills/`, `claude/plugin/hooks/` or a brief runs with the worker's permissions and, for hooks, outside the model. Rule for PCEE: take ideas, rewrite them, and never install ECC's plugin, hooks, installer (`install.sh`) or `ecc` package into a project that runs engine workers. In particular its `SessionStart` additional-context hook and `UserPromptSubmit` context-gate inject text into the model (`hooks/README.md`), the same channel the PCEE hold hooks rely on.
- **Maintenance and churn.** One maintainer ships "weekly across 7 harnesses" (`README.md`); the repo has 137 open issues and a stale-PR salvage ledger. Skills carry version numbers (continuous-learning-v2 is 2.1.0, delivery-gate 1.1.1) and adapters for harnesses PCEE does not use. Anything PCEE copies freezes at the copy; there is no upstream sync to rely on.
- **Scale of the catalogue.** The agents and skills lists are hundreds of files, many duplicated per language (`agents/` has a reviewer and a build-resolver for each language). Volume is not evidence of quality, and PCEE's own K2 gate is a better measure than star count.
- **What I did not read.** I read the files named in the table above plus `CLAUDE.md`, `SECURITY.md` and the directory listings. I did not read `ecc2/`, `scripts/` implementations, `hooks/hooks.json`, `docs/ECC-2.0-GA-ROADMAP.md`, `docs/gateguard/*` or `docs/SELECTIVE-INSTALL-ARCHITECTURE.md`. Claims about those are limited to what the listings and the files I did read say. I did not run any ECC code. Working copies of the files I read are in the session scratchpad and were not placed in the repo.

## Suggested follow-ups (for the lead to decide)

1. Add to the loop spec's Testing list: a case where a harmful change passes the signal but a guardrail stops it (insight 3).
2. Add to the loop spec: a per-trial spend cap, and "failures stay in the denominator" for tokens-per-task (insight 8).
3. Add to the engine spec §13 or §10: a hook that blocks a stop blocks once, then warns (insight 4).
4. Park, as an idea: a `retire` proposal kind with soft-delete and undo log (insight 5), and per-skill success rates (insight 10).
