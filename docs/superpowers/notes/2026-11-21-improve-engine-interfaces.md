## Row 2 verdict

`needs registration`. `engine rebuild --check` replays every event's `rows` into a scratch DB made by `db.open`, which creates only the tables in `SCHEMA` (`engine/lib/engine/db.js:8-25`). A `proposals` table that exists only in the live DB makes `putRaw` fail (`no such table: proposals`, rc=1). Task 3 must add `CREATE TABLE IF NOT EXISTS proposals(…)` to `SCHEMA` in `engine/lib/engine/db.js`. With that line the same probe gives `replay matches the live tables`, rc=0. The loop's `improve` events must carry their rows as `{table:"proposals", row}` in `detail.rows` (`db.event`, `db.js:105`). `rebuild.js` reads each table's key from `PRAGMA table_info` (`rebuild.js:12`), so no key list needs updating there; `core.js:46` `PK` lists keys only for the engine's own tables.

## Differences from the plan's wording

- Row 3: a `run-now` row's `source_id` is `<name>@now:<epoch>`, not `<name>@<due_at>` (`cli.js:573`).
- Row 6: there is no `runner` field on a metrics record; the engine-run marker is the non-null `budget`.
- Row 9: a review finding is event kind `review` with a count (`findings`) and the first text; the severities are only in the review job's `job_done` event (`status.findings`).
- Row 10: the defaults are the `DEFAULT_HOLDS` array; `engine.json` `holds` adds to them (no switch-off for a default). Task 11 decides whether its protected-path holds extend `DEFAULT_HOLDS` or go through `rulesFor` (`hold.js:28`).
