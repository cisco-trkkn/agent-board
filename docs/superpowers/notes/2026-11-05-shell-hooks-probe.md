Captured 2026-11-05, Claude Code run as `claude -p --plugin-dir <scratch> --allowedTools Bash Write Agent --model haiku`
(`--permission-mode bypassPermissions` was refused by the auto-mode classifier in this environment). The scratch probe mod
(`tool.check` and `tool.call` hooks that `await next(e)` and append `JSON.stringify({ev, e, out})` through
`$.fs.read` + `$.fs.write`) lives only in the session scratchpad. Logs cited as `L1` (main run, 21 lines), `L2` (deny run,

Probe gotchas that also apply to the real mods:

- `$.env.get(...)` returns a promise: `await` it. An un-awaited value passed to `$.fs.write` throws "arguments are not plain data".
- `tool.check` carries the arguments under `e.input` (`e.input.command`, `e.input.file_path`); `tool.call` carries them flat (`e.command`, `e.file_path`). Both have `e.tool`, `e.tool_use_id`, and `e.agentId` inside a subagent (L1:18, L1:19).
- Auto mode's classifier blocks a `Write` in this environment ("no verdict", L1:11) and `acceptEdits` flags the scratchpad path as "a sensitive file" (L4:2), so no Write ran to success.

## Answers

- (a) **Bash `tool.call`, `next(e)` result.** Success (`echo hi`): `{ ref: 1, result: { stdout: "hi", stderr: "", interrupted: false, isImage: false, noOutputExpected: false }, text: "hi", isReadOnly: true }` (L1:3). Failure (`false`, exit 1): `{ ref: 1, result: "Error: Exit code 1", text: "Exit code 1", isError: true, isReadOnly: true }` (L1:5). So stdout and stderr are `out.result.stdout` / `out.result.stderr` only on success; on a non-zero exit `result` is a string, `isError` is true, and the exit code exists only inside that string (`Exit code N`), with no stdout or stderr fields. `out.text` is the stdout (success) or the error text.
- (b) **Write `tool.call` result: not probed to success.** The Write was refused before running: L1:11 (`result: "Error: The server-side auto mode classifier gave no verdict…"`, auto mode), L3:3 and L4:3 (`result: "Error: Claude requested permissions …"`, `text` the same string without `Error: `, `isError: true`). So a failed or refused call has `result` as an "Error: …" string plus `isError: true`, as for Bash. The success shape is "not probed"; the reference doc (events.md, "Guard or change a tool call") says a refused call comes back as `{ deny }` and a failed one has `isError` set, and the built-in result type is in the types for the build (`claude-code.d.ts`). A Claude Docs / Artifact tool was not reachable from `-p`: not probed.
- (c) **Bash cwd.** `session.start`'s `e.cwd` is the start directory (L1:1; `surface: null`, `isInteractive: false` under `-p`); `$.process.run(['pwd'])` in a `tool.call` hook returns the same start directory for every call (`modpwd` in L1:3-L1:21), and `tool.call`'s `e` has no cwd field (L1:3). `cd /tmp && pwd` printed `/tmp` but its result stderr says `Shell cwd was reset to <start dir>` and the next `pwd` printed the start dir again (L1:7, L1:9): the cd was outside the allowed working directories, so a cd that sticks (inside the working dir) was not probed. Conclusion: a mod reads the Bash cwd only from `session.start`'s `e.cwd` (or `pwd` from `$.process.run`, which is the process cwd, not the shell's); neither tracks `cd`.
- (d) **`tool.check` deny.** Returning `{ decision: 'deny', reason }` without calling `next` blocks the call and shows the model `Permission to use Bash denied by plugins probe, cc-plugin-privacy: <reason>` as an error result (L2:4 hook, L2:5 `tool.call` out `isError: true`, the command's stdout never appears). Returning the same deny after `await next(e)` (the check had resolved `ask`, L2:6) blocks it identically (L2:8: `…denied by plugins probe, cc-plugin-privacy: PROBE-DENY-AFTER reason text`). Both reasons reached the model verbatim (the subagent-free run's final answer quoted them).
- (e) **Local time.** `new Date().toTimeString()` gave `15:33:10 GMT-0500 (Eastern Standard Time)`, `getHours()` 15, `getTimezoneOffset()` 300, and `date +%H:%M:%S` run through `$.process.run` in the same hook gave `15:33:10` (L1:1). So the mod runtime is on local time and `getHours()` etc. match the shell.
- (f) **Subagent.** `tool.call` and `tool.check` both fire for a subagent's Bash call with `e.agentId` set (`"a278aa56d08c5cf0e"`, L1:18 check, L1:19 call: `{ command: "echo sub", …, agentId }`). The Agent launch itself (no `agentId`) is L1:16-17; the subagent's final `SubagentHandback` tool also fires with `agentId` (L1:20-21).
